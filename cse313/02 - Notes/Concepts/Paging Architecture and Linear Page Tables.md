# Paging Architecture and Linear Page Tables

> 📖 **Reading Order:** Step 42 of 68 | **Module 7: Paging & Virtual Memory Systems**  
> ◄ **Previous:** [[Problem — Segmentation Address Translation and Buddy Memory Allocation]] | ► **Next:** [[Translation Lookaside Buffers and Hardware Caching]]

## Starting Point and the Problem

As demonstrated in [[Segmentation and External Fragmentation]], dividing memory into variable-sized logical segments (Code, Heap, Stack) solves internal void waste but introduces crippling **external fragmentation**. Free memory becomes divided into irregularly sized holes. When no single contiguous hole is large enough for a new segment, allocation fails—even when total free memory is abundant.

To eliminate external fragmentation entirely, the operating system must abandon variable-sized allocation.

---

## Developing the Idea: Fixed-Size Units

The fundamental insight of **Paging** is partitioning memory into fixed-size units:
1. The **Virtual Address Space** is split into fixed-size blocks called **Pages** (typically 4 KB).
2. **Physical Memory (RAM)** is split into matching fixed-size slots called **Page Frames** (or Physical Frames).

```
Virtual Address Space (Process):     Physical Memory (RAM Frames):
+---------------+ Page 0 (VPN 0)      +---------------+ Frame 0 (OS)
| Page 0        | ------------------> | Frame 1       |
+---------------+ Page 1 (VPN 1)      +---------------+
| Page 1        | ---------\          | Page 0 (PFN 2)|
+---------------+ Page 2    \         +---------------+
| Page 2        | -----\     -------> | Page 1 (PFN 3)|
+---------------+       \             +---------------+
                         -----------> | Page 2 (PFN 4)|
                                      +---------------+
```

### The Inherent Strengths of Paging:
- **Zero External Fragmentation:** Any virtual page can be placed in *any* available physical frame. Memory never requires compaction.
- **Extreme Flexibility:** The process address space no longer needs to be contiguous in physical RAM. Page 0 can sit at physical address 8 MB, while Page 1 sits at 2 MB.
- **Simple Free-Space Allocation:** The OS simply maintains a single free-frame bitmap or list. To allocate a 16 KB process, it pops any 4 free frames.

---

## How It Works: Address Translation Mechanics

In a paged system, every Virtual Address (VA) generated by the CPU is conceptually divided into two bitfields:
1. **Virtual Page Number (VPN):** Indexes which page of the address space is being accessed.
2. **Offset:** Selects the specific byte within that page.

```
32-Bit Virtual Address (with 4 KB = 2^12 Byte Pages):
+-------------------------------------------+-----------------------+
|        Virtual Page Number (VPN)          |     Offset Bits       |
|                 (20 bits)                 |       (12 bits)       |
+-------------------------------------------+-----------------------+
```

### Translation Equations:
$$\text{Offset Bits} = \log_2(\text{Page Size}) = \log_2(4096) = 12$$
$$\text{VPN Bits} = \text{Address Bits} - \text{Offset Bits} = 32 - 12 = 20$$
$$\text{VPN} = \text{Virtual Address} \gg 12$$
$$\text{Offset} = \text{Virtual Address} \ \& \ \text{0x00000FFF}$$
$$\text{Physical Address} = (\text{PFN} \ll 12) \mid \text{Offset}$$

The hardware MMU takes the VPN, looks it up in an in-memory data structure called the **Page Table**, retrieves the **Physical Frame Number (PFN)**, and appends the unchanged Offset to produce the final physical address!

---

## Anatomy of a Page Table Entry (PTE)

The simplest page table is a **Linear Page Table**—an array of **Page Table Entries (PTEs)** indexed directly by VPN:

```
PTE Format (x86 32-bit):
+---------------------------+---+---+---+---+---+---+---+---+
| Physical Frame Number PFN | G |PAT| D | A |PCD|PWT|U/S|R/W| P |
|         (20 bits)         |   |   |   |   |   |   |   |   |   |
+---------------------------+---+---+---+---+---+---+---+---+
```

Key flag bits stored in each PTE:
- **Present / Valid Bit ($P$):** $1$ if the page is currently loaded in physical RAM; $0$ if invalid or swapped out to secondary storage.
- **Read / Write Bit ($R/W$):** $1$ allows read and write; $0$ enforces read-only access (violating this raises a protection fault).
- **User / Supervisor Bit ($U/S$):** $1$ permits user-space access; $0$ restricts access to kernel mode only.
- **Dirty Bit ($D$):** Set by hardware MMU to $1$ whenever the page has been modified by a write instruction (critical for swapping).
- **Accessed / Reference Bit ($A$):** Set to $1$ whenever the page is read or written (used by page replacement policies like the Clock algorithm).

## The Two Critical Problems of Linear Paging

While paging solves external fragmentation, pure linear paging introduces two severe penalties:

### 1. The Space Problem (Gigantic Memory Overhead)
On a 32-bit system with 4 KB pages:
- Number of pages $= 2^{20} = 1,048,576$ pages.
- At 4 bytes per PTE, a single process page table requires:
  $$1,048,576 \times 4\,\text{bytes} = 4\,\text{MB of physical RAM!}$$
- If 100 processes run simultaneously, the OS must dedicate **400 MB of physical memory** purely to store page tables—most of which contain invalid entries for unused regions of the address space!

### 2. The Speed Problem (Double Memory Accesses)
Without hardware caching, every single memory reference requires **two physical memory accesses**:
1. Fetch the PTE from the in-memory page table: $\text{PTE Address} = \text{PTBR} + (\text{VPN} \times \text{sizeof(PTE)})$.
2. Fetch the actual instruction or data byte from physical RAM: $\text{Physical Address} = (\text{PFN} \ll 12) \mid \text{Offset}$.
This halves overall system performance!

Solving these two challenges requires hardware translation caching ([[Translation Lookaside Buffers and Hardware Caching]]) and hierarchical indexing ([[Multi-Level Page Tables and Advanced Address Translation]]).

## Example: Step-by-Step Numerical Walkthrough

Consider a system with a 64-byte virtual address space ($2^6 \implies 6$-bit addresses) and 16-byte pages ($2^4 \implies 4$-bit offset):
- VPN bits $= 6 - 4 = 2$ bits (Total 4 virtual pages: VPN 0, 1, 2, 3).
- Offset bits $= 4$ bits.
- Physical memory is 128 bytes ($2^7 \implies 7$-bit physical addresses, 8 frames: PFN 0 to 7).

Process Page Table:
- $\text{VPN 0} \to \text{PFN 7}$ (Valid)
- $\text{VPN 1} \to \text{PFN 5}$ (Valid)
- $\text{VPN 2} \to \text{PFN 2}$ (Valid)
- $\text{VPN 3} \to \text{Invalid}$

Translate Virtual Address `21` (Decimal):
1. Convert to binary: $21_{10} = \mathbf{01}\;0101_2$.
2. $\text{VPN} = 01_2 = 1$.
3. $\text{Offset} = 0101_2 = 5$.
4. Page table lookup: $\text{VPN 1}$ maps to $\text{PFN 5}$ ($101_2$).
5. Combine PFN and Offset:
   $$\text{PA} = (\text{PFN } 5 \times 16) + \text{Offset } 5 = (5 \times 16) + 5 = 80 + 5 = \mathbf{85} \quad (101\;0101_2).$$

## Important Properties and Why They Hold

- **Internal Fragmentation Invariant:** Because allocation is in units of pages, a process can only waste space on its *very last page*. The maximum internal fragmentation per process is $\text{Page Size} - 1$ byte (average $\frac{1}{2}\,\text{Page Size}$).
- **Translation Associativity Invariance:** Address translation operates strictly on the high-order bits (VPN); the low-order bits (Offset) pass through to the physical address completely unchanged.

---

## Common Mistakes

- **Assuming Page Tables Reside in the MMU:** Page tables are far too large to fit inside CPU silicon registers; they are stored in regular **physical RAM**. The MMU only holds the **Page Table Base Register (PTBR)** pointing to the table's starting RAM address.
- **Confusing VPN Bits with Address Space Size:** The number of VPN bits depends on the *page size*, not total physical RAM.
